# Magpie Bridge Architecture

网络结构 N:1 的 C-S 结构。

其中 S 为离散型转发节点，一个服务器可以十分高效地为众多客户端提供转发服务，但仅限于已在本服务器上注册的客户端。

服务器只为客户端提供最简单的转发服务，不与其他服务器关联。

## 服务器设计

服务器内部逻辑被设计为收发分离，即接收和转发各由单独的线程处理。

服务器在内存中维护一张 bid -> socket 信息映射表 yellow_pages。

### 0. 接收线程

服务器启动时绑定一个 UDP 端口，接收线程从该端口接收数据包之后，不做任何判断，直接将数据包与 socket 信息一起塞进预处理线程的等待列表中。

由于 UDP 只绑定一个端口，所以不会随着用户数增加而增加 fd 占用开销。

### 1. 预处理线程

从等待列表中取出数据包，

- 先对协议头进行校验，有任何错误就直接丢弃退出；
- 校验标志位 B=1（服务器只处理桥接包，B=0 的直连包不会发给服务器），否则直接丢弃退出；
- 取出 target bid，如果为 0 则交给管理线程（结束本包处理，由管理线程继续检查 source、command 等信息）；
- 取出 source bid，如果为 0 则说明错误，直接丢弃退出；
- 接着检查其对应的 socket 信息与 yellow_pages 中的记录是否匹配，不匹配则直接丢弃退出；
- 匹配一致则更新其活跃时间，然后指派给相应的转发线程等待处理。

备注： source bid 为 0 时 target bid 也必定为 0，这种情况只会在“第一次握手包”中存在；
反之，如果 source bid 为 0 的时候 target bid 不为 0，则属于错误包，可以直接丢弃。

### 2. 管理线程

从管理请求队列中取出数据包，然后判断是哪种类型的请求；若无法识别为下列任一类型（未知 command），直接丢弃退出。

#### 2.0. 第一次握手

判断依据： source bid == 0
> （此时 command 应为 "SYN?"，可选）

处理流程：从内存数据表中找到一个合适的空记录 bid，登记当前 socket 信息，然后回复 SYN+ACK 包（不指派转发线程）。

#### 2.1. 第三次握手

判断依据： command == "ACK!"
> （同时 source bid > 0，必须）

处理流程：取出 source bid，与内存数据表中的记录比较，如果 socket 不匹配就直接丢弃，一致则更新其活跃时间，然后指派转发线程。

#### 2.2. 心跳包

判断依据： command == "PING"
> （同时 source bid > 0，必须）

处理流程：按通讯协议标准回复 ```PONG```，同时更新其活跃时间。

#### 2.3. 挥手

判断依据： command == "FIN?"
> （同时 source bid > 0，可选）

处理流程：删除记录，释放 bid。

### 3. 转发线程（N条）

服务器启动时自动安排 N 条转发线程处理任务（默认 N=256），预处理线程在分配转发任务时需要先做一个处理：

- 计算 n = (source bid) % N
- 然后指派给第 n 条转发线程

转发线程内部为每个 source bid 创建一个等待转发队列，指派任务时直接将数据包放进相应的队列中。

#### 转发线程 runloop

为了公平起见，避免单个用户发送大量数据严重干扰其他用户的正常请求，这里轮训任务时采用“广度优先”策略：

- 轮询其辖下的 source bid，如果对应的等待转发队列不为空则取出最前面的数据包；
- 如果当前所有的 bid 都没有等待转发任务，则 sleep 一小段时间后继续下一个循环；
- 取出该包中的 target bid，检查 yellow_pages 中的记录是否存在并活跃，否则直接丢弃进入下一个循环；
- 将该数据包通过绑定的 UDP 接口发送给 target bid 所对应的 socket；

#### 流量控制

为了避免流量风暴，转发线程需要增加一个限流措施，比如设定一个在规定时间内最多处理多少任务的上限值。

由于系统将转发任务拆分给 N=256 条线程处理，所以单挑线程的任务达到上限不会影响其他线程，将风暴控制在一个很小的影响范围之内。
