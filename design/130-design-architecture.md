# Magpie Bridge Architecture （架构设计）

网络结构 N:1 的 C-S 结构。

其中 S 为离散型转发节点，一个服务器可以十分高效地为众多客户端提供转发服务，但仅限于已在本服务器上注册的客户端。

服务器只为客户端提供最简单的转发服务，不与其他服务器关联。

## 服务器架构设计

服务器内部逻辑被设计为收发分离，即接收和转发各由单独的线程处理。

服务器在内存中维护一张 bid record 分配表，同时为之建立两套索引：

1. bid - 客户端“门牌号”
2. key - 客户端 socket 信息字符串："{ip}:{port}"，

可以通过 bid 或 socket 信息直接查询记录。

> 在服务器的分配规则下， bid 和 socket 信息一一对应。
> 即：一个 bid 任何时候都只会成功分配给一个 socket，反之任意 socket 最多只能查到一条 bid 记录。

Record 属性见用户信息记录文档。

### 0. 接收线程

服务器启动时绑定一个 UDP 端口，接收线程从该端口接收数据包之后，不做任何判断，直接将数据包与 socket 信息一起（封装成“任务”对象）塞进预处理线程的等待列表中。

由于 UDP 只绑定一个端口，所以不会随着用户数增加而增加 fd 占用开销。

### 1. 预处理线程

从等待列表中取出下一个任务，

- 检查来源 IP 地址，如果是广播或多播地址则直接丢弃（不应答、不转发，防止放大攻击），进入下一循环；
- 然后解析数据包（对协议头进行校验），解析失败直接丢弃，进入下一循环；
- 接着校验标志位 B=1（服务器只处理桥接包，B=0 的直连包不会发给服务器），否则直接丢弃，进入下一循环；
- 取出 target bid，如果为 0 则交给管理线程（由管理线程继续检查 source、command 等信息），然后进入下一循环；
- 取出 source bid：如果为 0 或与 target bid 相等，则属于上行校验违规，直接丢弃（校验规则见服务器设计），进入下一循环；
- 其余情况（target 与 source 均非 0 且不相等的转发包）直接按 source bid 哈希指派给相应的转发线程等待处理：
	- 来源 socket 的绑定一致性校验、活跃时间更新以及转发/应答逻辑等均在转发线程内完成（见转发线程）。

备注： source bid 为 0 时 target bid 也必定为 0，且这种情况只会在“第一次握手包”中出现。

### 2. 管理线程

管理线程的每一个 runloop，先执行一次回收检查：
> 若距上次调用已超过 `record_recycle_interval`（默认 10 分钟），调用 purge(now) 回收超过 expires 的常规记录（详见服务器文档）。

然后从管理请求队列中取出下一个任务（队列为空时阻塞等待），

- 如果 command == "SYN?"，走“第一次握手”子流程（唯一允许 source bid 为 0 的情况），完成后进入下一个循环；
- 除此以外必须 source > 0，否则属于上行校验违规，直接丢弃然后进入下一个循环；
- 如果 command == "ACK!"，走“第三次握手”子流程（无状态令牌验证），完成后进入下一个循环；
- **【来源检查】**接下来按来源 socket 查询内存分配表，如果记录不存在，则按“连接未确认”处理：
    - 先回复 "FAIL" 通知客户端（防放大策略见安全提案）；
    - 然后丢弃该包并进入下一个循环；
- 如果 socket 记录存在（该 socket 已绑定 bid Z），则检查 source bid 是否等于 Z：
    - 不相等则判定为伪造来源，直接丢弃该包，进入下一个循环；
    - 相等则继续下一步（附加校验方法见安全提案）；
- **【离线分流】**如果记录 offline == true，且 command 不属于 "FIN?"/"NOOP"（"SYN?"/"ACK!" 已在前面处理）：
    - 静默丢弃（不更新活跃时间），进入下一个循环；
- **更新发送方记录的活跃时间**，然后继续下一步；
- **【指令集过滤】**最后检查 command 是否属于已支持的系统指令，若无法识别为下列任一类型（未知 command），直接丢弃然后进入下一个循环；
- 以上校验全部通过之后，按照 command 值走对应的子流程。

#### Secret

密钥分两种，

1. 服务器密钥：仅用于生成/校验 Token，只保管在服务器上（内存列表，10分钟更新一次）；
2. 客户端密钥：由服务器生成，通过握手过程发给客户端保存，握手成功后所有系统指令都必须用此密钥进行签名/验签；客户端密钥一旦确定，在 record 的生命周期内永不改变。

> 注：两种密钥的生成都必须用密码学安全随机数（以下同）。
> 服务器密钥永不外发，网络上完全不可见；但客户端密钥会在握手阶段发送，可能会被嗅探。

#### Token

Token 是一个字符串，由服务器按既定算法生成，用于握手阶段与客户端传递密钥 secret。

**生成规则**：

1. 取得 bid （新建/内定/预订/复用）十进制正整数
2. 取得 secret （如果是复用流程，则取原 record.secret，否则随机生成，然后 Base64 编码）
3. 观察得到客户端 socket (格式为 "{ip}:{port}" 的字符串)
4. 取服务器当前时间戳 time （秒，十进制正整数）
5. 按 key 字典序排序合并 "bid={bid}&secret={secret}&socket={socket}&time={time}"
6. 取最新的服务器密钥 server_secret 对该字符串计算 token（HMAC-SHA256）
7. 将计算结果用 Base64 进行编码。

**校验规则**：

1. 取 bid={协议头 source bid}
2. 取 socket={服务器观察到的来源 "{ip}:{port}"}
3. 取 secret={载荷中的 "secret"}
4. 取 time={载荷中的 "token_time"}
5. 按 key 字典序排序合并 "bid={bid}&secret={secret}&socket={socket}&time={time}"
6. 用所有服务器密钥（最多2个）逐个对该字符串重算 token（HMAC-SHA256），并与载荷中的 "token" 值（Base64编码字符串）进行比对，
7. 匹配一个则表示成功，全部密钥都不匹配则表示失败。

#### 2.1. 第一次握手

判断依据： command == "SYN?"
> （协议头 source bid 可为 0，也可为客户端预设的期望 bid）

处理流程（本阶段**不创建任何记录**，仅做分配决策并下发验证令牌，分配规则详见服务器文档）：

1. **【复用记录】** 先根据 socket 信息查询分配表，如果记录存在：
    - 则直接复用该记录中的 bid，无需再检查 source bid；
    - 客户端密钥 secret 则取原 record.secret；
2. **【预订流程】** 如果 socket 记录不存在，且 source bid 非 0，则走预订流程：
    - 无论来源是否 loopback，都要先检查该 bid 是否合法，不合法则回复 "FAIL" 指令包并_退出_；
        - 预订 bid 必须大于 65535，不能预订保留给 loopback 的“内定区间”，
    - 然后按该 bid 查表，如果 bid 记录已存在：
        - 即表示该 bid 已被其他 socket 占用，因为当前 socket 已确认过无绑定记录（见第一步），故记录存在则其 socket 必不相同；
        - 预订冲突，直接回复 "FAIL" 指令包并_退出_（由客户端决定是否重新申请）；
    - 记录不存在（空闲）则采用该 bid；
3. **【内定流程】** 如果 source bid 为 0，且来源 IP 为环回地址（loopback: 127.0.0.0/8, ::1/128）时：
    - 则按内定规则分配 bid = port；
    - 若该 bid 已被其他 socket 占用，直接回复 "FAIL" 指令包并_退出_；
4. **【正常分配】**否则按分配规则生成一个新 bid：
    - 分配不成功则回复 "FAIL" 指令包并_退出_；
5. 通过上述流程拿到 bid 之后，接下来便是客户端密钥 secret 和生成握手令牌 token：
    - 获取客户端密钥 secret（新分配/内定/预订时随机生成，复用记录时取原 record.secret），然后按上面的“Token 生成规则”得到 token 和 token_time；
    - 然后通过 "SYN!" 包下发给客户端，分配的 bid 放在协议头的 target 字段，其他信息以 JSON 格式编码后放入 payload（见载荷格式规范）

注：本阶段不登记 socket 信息、不保存客户端密钥、不创建 bid 记录，转发线程因查不到记录仍不转发其数据包，所有记录信息由客户端在 "ACK!" 中回传（见 2.1）。

> 由于 bid 与 socket 一一对应，所以如果按 socket 查不到记录，那按 bid 查出来的记录其 socket 信息必然和当前客户端的 socket 不同。

#### 2.2. 第三次握手（无状态验证 + 创建记录）

判断依据： command == "ACK!"
> （同时 source bid > 0，必须）

处理流程（记录尚未创建，验证完全基于令牌，不依赖任何服务器状态）：

- 协议头 source bid 已经在前面的步骤校验过了，其它信息也全部在第一次握手时校验过并用服务器密钥“锁死”在载荷中的 "token" 字段里；
- 接着用服务器密钥组（最多 2 个，见服务器文档密钥轮换）按上面的"Token 校验规则“对载荷中的 token 信息进行校验：
    - 全部服务器密钥都不匹配：判定为不可信来源，直接丢弃、不应答_退出_；
    - 如果能匹配一个，再检查载荷数据区 `token_time`：
        - 如果超出有效窗口（`handshake_token_timeout`，默认 60 秒）则回复 "FAIL" 指令包并_退出_，客户端需重新握手；
- 以上校验全部通过后，按 source bid 查询分配表（重复确认有效性）：
	- 记录不存在：创建 bid record（secret 取自载荷中的 "secret" 字段，last_time 为服务器当前时间），连接即已确认，此后转发线程方可转发其数据包；
	- 记录已存在且 socket 信息匹配（重复 "ACK!" 或重新握手场景）：幂等处理，更新其活跃时间 last_time、清除 offline 标记，secret 保持不变（不覆盖、不轮换）；
	- 记录已存在但 socket 信息不同（bid 竞态冲突）：回复 "FAIL" 指令包，客户端重新握手。

#### 2.3. 心跳包

判断依据： command == "PING"
> （同时 source bid > 0，必须）

处理流程：按通信协议标准回复 "PONG"。

> 校验策略：
>     客户端 socket、协议头的 source 以及载荷 payload 等已经在上一步的取任务过程中校验过了，
>     所以这里无需再次校验（以下同）；
>     
> 过滤策略：
>     已绑定客户端的应答不限频（见安全提案，以下同）。

#### 2.4. 挥手

判断依据： command == "FIN?"
> （同时 source bid > 0，必须）

处理流程：
- 若 record.last_noop_time 处于 `noop_immunity_window`（默认 2 秒）内：仅回复 "FIN!" 指令包（挥手应答），**不修改 offline**；
- 否则：先将记录标记为离线（offline），再回复 "FIN!" 指令包（挥手应答）；
- **不删除记录、不立即释放 bid**；记录仍按超时规则（purge）回收。转发线程可据此立即感知该客户端离线，无需等待活跃超时。

#### 2.5. 通行证管理

判断依据： command == "ACPT" 或 "DENY"
> （同时 source bid > 0，必须）

处理流程：

- 解析载荷（格式见载荷格式规范），取出 bid 列表；
- "ACPT"：逐个查询 bid record 分配表，按错误类型分类处理——**格式类错误**（bid 为负数、0、或等于发起方自身 bid）整体拒绝，回复 "FAIL"（载荷含 src-command 与格式非法的 bid 子集，见载荷格式规范）；**状态类错误**（记录不存在、空间不足）逐条跳过，继续处理其余 bid；对通过的 bid 按用户信息记录文档中的**添加流程**执行（先修改 Permit、再检查空间、空间足够才写入 A 侧 allowlist），全部处理完后存在失败条目则回复 "FAIL"（载荷含 src-command 与未成功的 bid 子集），全部成功则回复 "DONE"（载荷含 src-command 并回显实际写入的 bid 列表）；
- "DENY"：按用户信息记录文档中的**删除流程**执行（含清空标记判定）——格式类错误（负数、0、自身 bid）整体拒绝，回复 "FAIL"（载荷含 src-command 与格式非法的 bid 子集）；否则逐个删除（目标记录或通行证不存在亦视为成功，幂等），完成后回复 "DONE"（数据区含 src-command 并回显实际删除的 bid 列表，清空时回显被清空的 bid 列表）；
- 通行证列表保存在记录上，随记录回收（purge）自动删除，无需额外清理。

#### 2.6. 空操作

判断依据： command == "NOOP"
> （同时 source bid > 0，必须）

处理流程：清除记录中的 offline 标记，并将 record.last_noop_time 更新为当前服务器时间（免疫窗口随之续期，见安全提案），然后**不应答**（无应答指令，客户端以此实现秒级自愈，见 2.3）。

### 3. 转发线程（W条）

服务器启动时自动安排 W 条转发线程处理任务（默认 W=8），预处理线程在分配转发任务时需要先做一个处理：

- 计算 n = (source bid) % W
- 然后指派给第 n 条转发线程

转发线程内部为每个 source bid 创建一个等待转发队列，指派任务时直接将任务放进相应的队列中。

#### 转发线程 runloop

为了公平起见，避免单个用户发送大量数据严重干扰其他用户的正常请求，这里轮询任务时采用“广度优先”策略：

- 轮询其辖下的 source bid，如果对应的等待转发队列不为空则取出最前面的任务；
- 如果当前所有的 bid 都没有等待转发任务，则 sleep 一小段时间后继续下一个循环；
- **【来源检查】**先按来源 socket 查询内存分配表，如果记录不存在，则按“连接未确认”处理：
    - 先回复 "FAIL" 通知客户端（防放大策略见安全提案）；
    - 然后丢弃该包并进入下一个循环；
- 如果 socket 记录存在（该 socket 已绑定 bid Z），则检查 source bid 是否等于 Z：
    - 不相等则判定为伪造来源，直接丢弃该包，进入下一个循环；
    - 相等则继续下一步（附加校验方法见安全提案）；
- **【离线分流】**如果记录 offline == true：
    - 静默丢弃（不更新活跃时间），进入下一个循环；
- **更新发送方记录的活跃时间**，然后继续下一步；
- **【目标检查】**接下来取出该包中的 target bid，检查 bid record 记录表中的是否存在相应的记录，如果不存在：
    - 因为 bid record 回收时间长（默认 24 小时），正常操作一般不会遇到这种情况，所以可能是伪造包；
    - 静默丢弃，进入下一个循环；
- **【通行证检查】**检查发送方是否有权向 target 发送（规则见用户信息记录文档）：
    - 先在发送方记录的 allowlist 中查找 target 的通行证，若不存在，再在 target 记录的 allowlist 中查找发送方的通行证；
    - 命中后校验来源 socket 与本通行证匹配（Permit.match），再判定有效（Permit.valid）；
    - 任一边查到有效且来源匹配的通行证即放行（防止一方被攻击者强行删掉通行证，见安全提案）；
    - 若均不满足：静默丢弃（不应答、不转发，防止暴露收件人的存在与接纳状态），进入下一个循环；
    - 若命中有效通行证（发送方已被接纳）：继续下一步；
- **【目标状态】**检查 target 记录的活跃状态，如果 offline == true，或 last_time 超过 T_active（在线判定窗口，默认 60 秒）：
    - 此时 target 已不可达，发送方已确认被收件人接纳，可以回复 “FAIL” 通知发送方（防攻击策略见安全提案，payload 见载荷格式规范）；
    - 处理完之后进入下一个循环；
- **【完整转发】**以上所有检查校验全部通过，可以转发：
    - 将该数据包原封不动地通过绑定的 UDP 接口发送给 target bid 所对应的 socket；
    - 然后继续下一轮循环。

#### 流量控制

为了避免流量风暴，转发线程需要增加一个限流措施（设定一个在规定时间内最多处理多少任务的上限值）。

由于系统将转发任务拆分给 W=8 条线程处理，所以单条线程的任务达到上限不会影响其他线程，将风暴控制在一个很小的影响范围之内。

采用**滑动窗口**方式限流，具体窗口时长、每窗口处理上限与队列容量等参数详见服务器设计文档。
