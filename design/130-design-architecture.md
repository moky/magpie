# Magpie Bridge Architecture

网络结构 N:1 的 C-S 结构。

其中 S 为离散型转发节点，一个服务器可以十分高效地为众多客户端提供转发服务，但仅限于已在本服务器上注册的客户端。

服务器只为客户端提供最简单的转发服务，不与其他服务器关联。

## 服务器设计

服务器内部逻辑被设计为收发分离，即接收和转发各由单独的线程处理。

服务器在内存中维护一张 bid record 记录表，索引为 bid 和 socket 信息字符串："{ip}:{port}"，
可以通过 bid 或 socket 信息直接查询。

> 在服务器的分配规则下， bid 和 socket 信息一一对应。
> 即：一个 bid 任何时候都只会成功分配给一个 socket，反之任意 socket 最多只能查到一条 bid 记录。

Record 属性：

- bid       (**门牌号**)
- key       (**客户端索引** "{ip}:{port}")
- socket    (**客户端信息** ip, port)
- secret    (**客户端密钥**)
- last_time (最后活跃时间)
- offline   (主动下线标志)
- allowlist (通行证列表)

注：

1. 其中 bid、key、socket 和 secret 均为不变量，记录一经创建永不改变；
2. 每次收到有效数据包时都需要更新 last_time；
3. 通行证列表 allowlist 的元素是 (bid, key) 二元组。

### 0. 接收线程

服务器启动时绑定一个 UDP 端口，接收线程从该端口接收数据包之后，不做任何判断，直接将数据包与 socket 信息一起塞进预处理线程的等待列表中。

由于 UDP 只绑定一个端口，所以不会随着用户数增加而增加 fd 占用开销。

### 1. 预处理线程

从等待列表中取出数据包，

- 来源 IP 为广播或多播地址（IPv4 224.0.0.0/4 与 255.255.255.255、IPv6 ff00::/8 等）直接丢弃，不应答、不转发（防止放大攻击）；
- 然后解析数据包（对协议头进行校验），解析失败直接丢弃_退出_；
- 接着校验标志位 B=1（服务器只处理桥接包，B=0 的直连包不会发给服务器），否则直接丢弃_退出_；
- 取出 target bid，如果为 0 则交给管理线程（结束本包处理，由管理线程继续检查 source、command 等信息）；
- 取出 source bid：如果为 0 或与 target bid 相等，则属于上行校验违规，直接丢弃_退出_（校验规则见服务器设计）；
- 其余情况（target 与 source 均非 0 且不相等的转发包）直接按 source bid 哈希指派给相应的转发线程等待处理——来源 socket 的绑定一致性校验、活跃时间更新以及转发/应答逻辑均在转发线程内完成（见转发线程）。

备注： source bid 为 0 时 target bid 也必定为 0，这种情况只会在“第一次握手包”中存在。

### 2. 管理线程

从管理请求队列中取出数据包，

- 如果 command == "SYN?"，走“第一次握手”子流程（唯一允许 source bid 为 0 的情况）；
- 除此以外必须 source > 0，否则属于上行校验违规，直接丢弃_退出_；
- 如果 command == "ACK!"，走“第三次握手”子流程（无状态令牌验证）；
- **【来源检查】**接下来按来源 socket 查询内存分配表，如果记录不存在，则按“连接未确认”处理：
    - 检查 command 是否为 PING/ACPT/DENY（只有这 3 条指令需要错误提示），如果是：
        - 下一步检查载荷长度是否达到最低要求（```manager_min_payload```，默认 100 字节），是则回复 "FAIL" 通知客户端：
            - 载荷文本头带 mp-src-command 回显被拒指令
            - 无密钥，不带 mp-verify
            - 载荷数据区为服务器观察到的来源地址 ```{"UDP":"ip:port","time":...}```
            - 客户端可据此补发 "ACK!" 或重新握手；
    - 然后丢弃该包_退出_；
- 来源 socket 记录存在（连接已确认），则检查 source bid 是否与记录中的 bid 相同：
    - 不同则判定为伪造来源（socket 已被绑定却上报不同的 bid），直接丢弃该包、不应答_退出_；
    - 相同则校验其载荷文本头 mp-verify（HMAC-SHA256，对数据区全部字节计算，与 record.secret 比对）；
        - 校验失败视为不可信来源，直接丢弃该包、不应答_退出_；
- **【指令集过滤】**最后检查 command 是否属于已支持的系统指令，若无法识别为下列任一类型（未知 command），直接丢弃_退出_；
- 以上校验全部通过之后，**更新活跃时间**```record.last_time = now```，然后按照 command 值走对应的子流程。

备注：凡 record 已建立（连接已确认）后收到的系统指令（"SYN?" 与 "ACK!" 除外），均需先校验载荷（见载荷文档）。

如果管理请求队列为空（管理线程空闲），则执行回收职责：按 record_recycle_interval（默认 10 分钟）调用 purge(now) 回收超过 expires 的常规记录（详见服务器文档）。

#### Secret

密钥分两种，

1. 服务器密钥：仅用于生成/校验 Token，只保管在服务器上（内存列表，10分钟更新一次）；
2. 客户端密钥：由服务器生成，通过握手过程发给客户端保存，握手成功后所有系统指令都必须用此密钥进行签名/验签；客户端密钥一旦确定，在 record 的生命周期内永不改变。

> 注：两种密钥的生成都必须用密码学安全随机数。

#### Token

Token 是一个字符串，由服务器按既定算法生成，用于握手阶段与客户端传递密钥 secret。

**生成规则**：

1. 取得 bid （新建/内定/预订/复用）
2. 取得 secret （如果是复用流程，则取原 record.secret，否则随机生成）
3. 观察得到客户端 socket
4. 取服务器当前时间 time
5. 按 key 字典序排序合并 "bid={bid}&secret={secret}&socket={socket}&time={time}"
6. 取最新的服务器密钥 server_secret 对该字符串计算 token（HMAC-SHA256）
7. 将计算结果用 Base64 进行编码。

**校验规则**：

1. 取 bid={协议头 source bid}
2. 取 secret={载荷包头 mp-secret}
3. 取 socket={服务器观察到的来源 ip:port}
4. 取 time={数据区 token_time}
5. 按 key 字典序排序合并 "bid={bid}&secret={secret}&socket={socket}&time={time}"
6. 用所有服务器密钥（最多2个）逐个对该字符串重算 token（HMAC-SHA256），并与数据区的 "token" 值（Base64编码字符串）进行比对，
7. 匹配一个则表示成功，全部密钥都不匹配则表示失败。

#### 2.0. 第一次握手

判断依据： command == "SYN?"
> （协议头 source bid 可为 0，也可为客户端预设的期望 bid）

处理流程（本阶段**不创建任何记录**，仅做分配决策并下发验证令牌，分配规则详见服务器文档）：

1. **【复用记录】** 先根据 socket 信息查询内存分配表，如果记录存在：
    - 则直接复用该记录中的 bid，无需再检查 source bid；
    - 客户端密钥 secret 则取原 record.secret；
2. **【预订流程】** 如果 socket 记录不存在，且 source bid 非 0，则走预订流程：
    - 无论来源是否 loopback，都要先检查该 bid 是否合法，不合法则直接回复 "FAIL" 指令包并_退出_；
        - 预订 bid 必须大于 65535，不能预订保留给 loopback 的“内定区间”，
    - 然后按该 bid 查表，如果 bid 记录已存在：
        - 即表示该 bid 已被其他 socket 占用，因为当前 socket 已确认过无绑定记录（见第一步），故记录存在则其 socket 必不相同；
        - 预订冲突，直接回复 "FAIL" 指令包并_退出_（由客户端决定是否重新申请）；
    - 记录不存在（空闲）则采用该 bid；
3. **【内定流程】** 如果 source bid 为 0，且来源 IP 为环回地址（loopback: 127.0.0.0/8, ::1/128）时：
    - 则按内定规则分配 bid = port；
    - 若该 bid 已被其他 socket 占用，直接回复 "FAIL" 指令包并_退出_；
4. **【正常分配】**否则按分配规则生成一个新 bid：
    - 分配不成功则回复 "FAIL" 指令包并_退出_；
5. 通过上述流程拿到 bid 之后，接下来便是客户端密钥 secret 和生成握手令牌 token：
    - 获取客户端密钥 secret（新分配/内定/预订时随机生成，须用密码学安全随机数；复用记录时取原 record.secret），按上面的“Token 生成规则”得到 token 和 token_time；
    - 然后通过 "SYN!" 包下发给客户端：载荷文本头携带 mp-secret（Base64 编码的 secret），载荷数据区携带 socket 信息、token 与 token_time（服务器生成时间）；
    - 给客户端分配的 bid 放在协议头的 target bid 字段；
    - 本阶段不登记 socket 信息、不保存客户端密钥、不创建 bid 记录，转发线程因查不到记录仍不转发其数据包，所有记录信息由客户端在 "ACK!" 中回传（见 2.1）。

> 注：由于 bid 与 socket 一一对应，所以如果按 socket 查不到记录，那按 bid 查出来的记录其 socket 信息必然和当前客户端的 socket 不同。

#### 2.1. 第三次握手（无状态验证 + 创建记录）

判断依据： command == "ACK!"
> （同时 source bid > 0，必须）

处理流程（记录尚未创建，验证完全基于令牌，不依赖任何服务器状态）：

- 协议头 source bid 已经在前面的步骤校验过了，其它信息也全部在第一次握手时校验过并用服务器密钥“锁死”在载荷数据区的 "token" 字段中；
- 接着用服务器密钥组（最多 2 个，见服务器文档密钥轮换）按上面的"Token 校验规则“对载荷中的 token 信息进行校验：
    - 全部服务器密钥都不匹配：判定为不可信来源，直接丢弃、不应答_退出_；
    - 如果能匹配一个，再检查载荷数据区 ```token_time```：
        - 如果超出有效窗口（```handshake_token_timeout```，默认 60 秒）则回复 "FAIL" 指令包并_退出_，客户端需重新握手；
- 以上校验全部通过后，按 source bid 查内存分配表（重复确认有效性）：
	- 记录不存在：创建 bid record（secret 取自载荷头部的 mp-secret 字段，last_time 为服务器当前时间），连接即已确认，此后转发线程方可转发其数据包；
	- 记录已存在且 socket 信息匹配（重复 "ACK!" 或重新握手场景）：幂等处理，更新其活跃时间 last_time、清除 offline 标记，secret 保持不变（不覆盖、不轮换）；
	- 记录已存在但 socket 信息不同（bid 竞态冲突）：回复 "FAIL" 指令包，客户端重新握手。

#### 2.2. 心跳包

判断依据： command == "PING"
> （同时 source bid > 0，必须）

处理流程：按通信协议标准回复 "PONG"。

注：
客户端 socket、协议头的 source bid 以及载荷 payload 等已经在上一步的取包过程中校验过了，
所以这里无需再次校验（以下同）。

#### 2.3. 挥手

判断依据： command == "FIN?"
> （同时 source bid > 0，必须）

处理流程：先将记录标记为离线（offline），再回复 "FIN!" 指令包（挥手应答），**不删除记录、不立即释放 bid**；记录仍按超时规则（purge）回收。转发线程可据此立即感知该客户端离线，无需等待活跃超时。

#### 2.4. 通行证管理

判断依据： command == "ACPT" 或 "DENY"
> （同时 source bid > 0，必须）

处理流程：

- 解析载荷（遵循载荷文档格式）：数据区为 JSON，形如 ```{"sources":[bid, ...]}```，取出 bid 列表；
- 逐个检查列表中 bid 是否有效（bid record 记录表中存在即有效），然后取出 record.key 组成二元组 (bid, key)；
- 全部有效：按指令类型将上一步得到的所有二元组全部加入/移出发起者的记录（通行证列表 record.allowlist），然后回复 "DONE"（数据区回显原 bid 列表）；
- 任一无效：整体不执行（原子性），回复 "FAIL"（数据区为未通过校验的 bid 子集）；
- 幂等："ACPT" 添加已存在的通行证、"DENY" 移除不存在的通行证均视为成功；
- 通行证列表保存在记录上，随记录回收（purge）自动删除，无需额外清理。

#### 2.5. 空操作

判断依据： command == "NOOP"
> （同时 source bid > 0，必须）

处理流程：清除记录中的 offline 标记（活跃时间已由管理线程总则统一更新），然后**不应答**（无应答指令，客户端以此实现秒级自愈，见 2.3）。

### 3. 转发线程（W条）

服务器启动时自动安排 W 条转发线程处理任务（默认 W=8），预处理线程在分配转发任务时需要先做一个处理：

- 计算 n = (source bid) % W
- 然后指派给第 n 条转发线程

转发线程内部为每个 source bid 创建一个等待转发队列，指派任务时直接将数据包放进相应的队列中。

#### 转发线程 runloop

为了公平起见，避免单个用户发送大量数据严重干扰其他用户的正常请求，这里轮训任务时采用“广度优先”策略：

- 轮询其辖下的 source bid，如果对应的等待转发队列不为空则取出最前面的数据包；
- 如果当前所有的 bid 都没有等待转发任务，则 sleep 一小段时间后继续下一个循环；
- **【来源检查】**先按来源 socket 查询内存分配表，如果记录不存在（来源 socket 无绑定记录）：
    - 对正常用户而言，通常有两种情况：
        1. 第三次握手包 "ACK!" 丢失，从服务器角度看客户端尚未完成握手；
        2. 客户端换网络，socket 发生改变；
    - 不管哪种情况，先判断协议 payloadLength 是否达到防放大门槛 unconfirmed_min_payload（默认 256 字节，见服务器文档），没达到则静默丢弃（防放大攻击）；
    - 达到要求的数据包，则以 "FAIL"（载荷数据区为服务器观察到的来源地址，UDP 字段格式同 "SYN!"，文本头带 mp-src-command 回显被拒指令的 command，不带 mp-verify）通知客户端再丢弃该包；
    - 处理完毕进入下一个循环；
- 如果 socket 记录存在（该 socket 已绑定 bid Z），则检查 source bid 是否等于 Z：
    - 不相等则判定为伪造来源，直接丢弃该包，进入下一个循环；
    - 相等（source 与记录匹配）则**更新发送方记录的活跃时间**，然后继续下一步；
- **【目标检查】**接下来取出该包中的 target bid，检查 bid record 记录表中的是否存在相应的记录，如果不存在：
    - 因为 bid record 回收时间长（默认 24 小时），正常操作一般不会遇到这种情况，所以可能是伪造包；
    - 静默丢弃，进入下一个循环；
- 检查 target 记录的活跃状态，如果 offline == true，或 last_time 超过 T_active（在线判定窗口，默认 60 秒）：
    - 此时 target 已不可达，需要决定是否通知发送方“目标已离线”；
    - 检查当前用户是否在 target 的通行证列表中，如果不在：
        - 即 target 的通行证列表 allowlist 里不存在二元组 (source bid, 当前客户端 key)；
        - 静默丢弃（不应答、不转发，防止暴露收件人的存在与接纳状态）；
    - 如果在通行证列表中（发送方已被收件人通过 "ACPT" 接纳），可以回复 "FAIL" 通知发送方；payload 遵循载荷文档格式：
        - 文本头携带 mp-src-command 以回显被拒数据包的 command（如 "DATA"）
        - 携带收件人 mp-src-target: {bid，十进制整数}
        - 携带校验值 mp-verify （发送方记录已确认、服务器有发送方的 secret，可计算校验值）；
        - 数据区仅含当前服务器时间 ```{"time":...}```
    - 处理完之后进入下一个循环；
- **【完整转发】**以上所有检查校验全部通过，可以转发：
    - 将该数据包原封不动地通过绑定的 UDP 接口发送给 target bid 所对应的 socket；
    - 然后继续下一轮循环。

#### 流量控制

为了避免流量风暴，转发线程需要增加一个限流措施（设定一个在规定时间内最多处理多少任务的上限值）。

由于系统将转发任务拆分给 W=8 条线程处理，所以单条线程的任务达到上限不会影响其他线程，将风暴控制在一个很小的影响范围之内。

采用**滑动窗口**方式限流，具体窗口时长、每窗口处理上限与队列容量等参数详见服务器设计文档。
